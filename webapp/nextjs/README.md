# Next.js実装（フロントエンド）

このディレクトリは Next.js（App Router）によるフロントエンド実装です。

バックエンドAPIの起動方法や全体構成は [webapp/README.md](../README.md) を参照してください。

## 前提条件

- Node.js 20 以上
- npm
- PostgreSQL 16（`webapp/docker-compose.yml` で起動）

## セットアップ

```bash
npm install
```

## データベース起動

`webapp` ディレクトリで以下を実行:

```bash
docker compose up -d db
```

初期化SQLは `webapp/sql/schema.sql` です。

## 起動

```bash
npm run dev
```

起動後、`http://localhost:3000` を開いてください。

## npmコマンド一覧

- `npm run dev`: 開発サーバーを起動
- `npm run build`: 本番用ビルドを作成
- `npm run start`: ビルド済みアプリを起動
- `npm run lint`: ESLintを実行

## 連携API

- `GET /press-releases/:id`
- `POST /press-releases/:id`

API仕様は [webapp/README.md](../README.md) を参照してください。

## 制作背景（課題・目的）

本プロジェクトは PRtimes ハッカソン参加時に制作した、\
中小企業の方が使いやすいプレスリリース作成エディタを目指すものです。

課題:
- 中小企業の広報担当は兼業で記事作成することが多く、時間的余裕がない。
- 費用対効果が不明瞭なため高コストをかけにくい。

目的:
- 生成AIを活用して下書き作成を支援し、作業時間を短縮する。
- 運営（編集側）が採用判断やガイダンスを行えるよう、下書きに対して「改善アドバイス」や「類似事例の提示」ができる仕組みを備える。

運用イメージ:
- まず生成AIで下書きを作成。AIだけでは表現しづらい“熱意”や固有の背景は、運営が最終調整やアドバイスを行い、メディア採用率を高める。

## 技術選定とその意図

- Next.js (App Router, React 19)
	- 理由: このプロダクトでは、React の開発体験を活かしつつ、初期表示の高速化と静的公開を同じコードベースで実現したかったためです。Next.js はファイルベースのルーティング、App Router によるレイアウト管理、サーバーコンポーネント、そして SSR/SSG への対応を標準で提供します。これにより、単純な React SPA よりも開発効率を優先しつつ、AWS S3 への静的エクスポートや API 連携の柔軟性を確保できます。
	- 運用面: このリポジトリでは実際に AWS S3 への `next export` 結果をデプロイする想定です。したがって、Next.js の「静的公開もサーバーサイドレンダリングも同じ設計で扱える柔軟性」が本番運用に合致しています。
	- チーム事情: 私自身と開発メンバーは React に慣れているため、既存の React 知識をそのまま Next.js に活かせる点も重視しました。
- TanStack Query
	- 理由: クライアント側のデータ取得・キャッシュ管理を安定させ、APIが不安定な開発環境でもモックとの切替が容易。
- TipTap（エディタ）
	- 理由: 課題において使用必須であったため。リッチテキスト編集と拡張性に優れ、中小企業向けに直感的な編集UXを提供。
## フロントのみを GitHub にあげて動かす可否

- フロントだけをリポジトリ（例: `webapp/nextjs`）として切り出し、GitHub に公開することは可能です。
- 注意点:
	- 実際に動かすには本番APIが必要ですが、開発/デモ目的であればモックAPI（`USE_MOCKS=1` 環境）を使ってフロント単体で動作確認できます。
	- 本番公開（Vercel / Netlify 等）する際は、外部APIのエンドポイントや環境変数（API_BASE_URL 等）の設定が必要です。

## ローカルでフロント単体（モック）を動かす手順

1. `webapp/nextjs` に移動して依存をインストール

```powershell
cd webapp/nextjs
npm install
```

2. モック有効化して開発サーバーを起動

```powershell
$env:USE_MOCKS='1'
npm run dev
```

3. ブラウザで `http://localhost:3000` を開く

モック有効時は API 呼び出しが内部の Next.js API ルートで処理され、バックエンドを起動せずにフロントだけ確認できます。

## 本物APIと連携して動かす手順（任意）

1. `webapp/php` 側で依存をインストールし、PHP サーバーを起動

```powershell
cd webapp/php
composer install
php -S 127.0.0.1:8000 -t public public/index.php
```

2. Next を通常モードで起動（モック解除）

```powershell
Remove-Item env:USE_MOCKS -ErrorAction SilentlyContinue
cd webapp/nextjs
npm run dev
```

## 補足: コメント機能と運営向けアドバイス

- 運営が下書きに対してコメントや改善アドバイス、類似事例を提示できる「コメント機能」を実装済み/予定です。フロント側ではコメントUIとAPIのモックを用意しておけば、運用時の検証が容易になります。

## SSR（サーバーサイドレンダリング）について

- 現在、アプリケーションのページはサーバーコンポーネントを用いて初期データをサーバー側で取得し、必要なクライアント専用コンポーネント（エディタやフォーム等）に初期データを渡す設計にしています。
- 具体的には:
	- `app/*/page.tsx` 等のページファイルで `fetch()` をサーバー側で実行して初期データを取得します。
	- TipTap を使ったリッチエディタやフォーム操作など、ブラウザでの相互作用が必要な部分はクライアントコンポーネント（`'use client'`）に切り出して扱います。
	- ルートレイアウト（`app/layout.tsx`）は `QueryClientProvider` をクライアント側で提供するためクライアントコンポーネントのままです。

- 利点:
	- 初回表示がサーバーでレンダリングされるため、初回表示速度（FCP/CLS）やSEOが改善されます。
	- クライアント側の JS を待たず表示できるため、ネットワークが遅い環境でも体感速度が向上します。

- 運用上の注意:
	- サーバー側 fetch により外部 API（PHP）への呼び出しが発生するため、本番デプロイ時は API のエンドポイントや認証、タイムアウト設定に注意してください。
	- クライアントコンポーネントに渡す初期データは JSON シリアライズされるため、循環参照や大きすぎるデータは避ける設計を推奨します。
